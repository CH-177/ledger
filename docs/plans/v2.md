# Ledger V2: scope

Status: **agreed** (September 27, 2026). Decisions are at the end. Building starts with #4 (2.0.0).

V2 adds six features to the finished V1 (see `docs/V1.md`). V1's principles still hold:
- Everything stays on this PC.
- Nothing is saved without the user seeing it first.
- Actual, planned and forecast money never mix.
- Every rule is written in `docs/RULES.md` and tested.

## Summary

| # | Feature | Size | Builds on | Version |
|---|---|---|---|---|
| 4 | Paycheck deductions and paystub check | S | Tax calculator already supports pre-tax deductions | **2.0.0 (done)** |
| 1 | Bank CSV import with review | L | `ExternalId` (exists) | **2.3.0 (done)**, fixes 2.3.1–2.3.2 |
| 2a | Refunds | M | Transaction types, every total | **2.4.0 (done)** |
| 6 | Smart suggestions (autofill) | M | Payee suggestions (exist) | **2.5.0 (done)** |
| 2b | Statement reconciliation | M | "Reconciled" status (exists), 1 | **2.6.0 (done)** |
| 3 | Sinking funds | M | Budget, Goals | **2.9.9 (done)** |
| 5 | Scenario planning | L | Forecast, paycheck predictions, goals | **2.9.9 (done)** |

Import was built before refunds and autofill (the user's choice), so versions were renumbered on
September 29, 2026 to keep going up: the rest of V2 is 2.5 to 2.8.

S ≈ one working session, M ≈ two or three, L ≈ four or more, each including tests, docs and a
UI click-through.

### Recommended order, and why it differs from the list

1. **Paycheck deductions and paystub check first (#4).** It's small, most of the math exists, and
   it's timely: the first real Riverside Market paystub arrives in early October. It also confirms the
   assumed payday.
2. **Refunds before import (#2a).** Bank and card exports are full of refunds and credits. If
   import comes first, they'd land as "income" and have to be fixed later.
3. **Suggestions before import (#6).** Import needs to guess a category for every row. That's the
   same engine as autofill, so it's built once and used in both places.
4. **Import (#1), then reconciliation (#2b).** Reconciling against a statement is much easier once
   statement rows can be imported.
5. **Sinking funds (#3), then scenarios (#5).** Scenarios are most useful once sinking funds and
   deductions exist, so "Can I afford this?" can account for them.

## 4. Paycheck deductions and paystub check (2.0.0, S)

**Goal:** paycheck estimates you can tune to match your real pay.

**What exists:**
- `PayrollTaxCalculator` already takes `PreTaxRetirementCents` and `PreTaxHealthCents` and applies
  each tax's rules. Federal excludes both. FICA excludes Section 125 health only. PA and local tax
  exclude health only, so 401(k) is taxed in PA.
- Jobs have no place to store deductions yet.

**Build:**
- Job deductions, each with name, kind and amount:
  - Kinds: pre-tax retirement (a % of gross or a fixed amount), pre-tax health/dental/vision
    (Section 125, fixed per paycheck), and after-tax (Roth 401(k), union dues).
  - Each has an effective date, like pay rates, so a benefits change doesn't rewrite old estimates.
- **After-tax deductions:** a new line kind in the calculator, subtracted after tax.
- **Paystub check:** when recording a paycheck, optionally enter the paystub's gross, federal,
  Social Security, Medicare, PA, local and net amounts.
  - Ledger shows a line-by-line comparison with its estimate and explains likely causes.
    Examples: a gross mismatch means hours or rate differ; a federal mismatch usually means W-4
    settings; an LST mismatch means a different work location.
  - Stubs are saved with the paycheck record, so estimates can be checked over time.
- **Payday confirmation:** the first recorded paystub offers to set the job's real payday.

**Rules to write down:** which deductions reduce which tax's base (already researched in
`income-calculator.md` §2.2), and that a paystub never changes the stored estimate.

**Tests:** each deduction kind against hand-worked examples, percent-of-gross rounding, effective
dates, and the paystub comparison.

**Open question:** does Riverside Market take any deductions from your pay now (health plan, 401(k)
match enrollment)? If not, the paystub check matters more than the deductions.

## 2a. Refunds (2.1.0, M)

**Goal:** a refund reduces spending in its category. It's never income and never inflates the
income figure.

**Design:**
- A new transaction kind, **Refund** (enum value 3, appended so existing data is untouched).
  - Money comes into an account, and it uses a **spending** category.
  - A refund can optionally link to the original purchase, which suggests its account and category.
- **Effect on totals:** a refund reduces spending for its category and month (budget, dashboard,
  reports, cash flow). It adds to the account balance. It never counts as income.
  - A refund in a later month reduces that later month's spending (cash basis). This choice
    matters and will be written down in RULES.md.
  - Budget "spent" can go below zero for a category. It's shown as "−$12.00 (refund)", never
    hidden.
- **Places that change:** transaction validation, all totals (TransactionService, BudgetService,
  DashboardService, ReportService), forecast signs, the CSV "Signed amount" column, and the
  transaction editor (a fourth kind).
  - The JSON export gains `"type": "refund"`. That's a new value, so the export format goes to
    **version 2**.
- **Existing data:** nothing is converted automatically. Past refunds recorded as income can be
  changed to Refund with the editor.

**Tests:**
- Extend `InvariantTests`: money is still conserved, and every page still agrees with refunds in
  the mix.
- A refund in the same month, a later month, and a month with no other spending.
- A refund on a credit card: this lowers what's owed.

## 6. Smart suggestions (autofill) (2.2.0, M)

**Goal:** fewer keystrokes for things you enter repeatedly, and spotting repeating spending that
could be a bill. **It suggests only: nothing is filled in without being shown, and nothing is
saved automatically.**

**What exists:** typing a payee suggests past payees and fills the category they were last used
with.

**Build:**
- **Learn from history** with one `SuggestionService` in Core, used by manual entry and later by
  import.
  - For a payee, suggest the **usual category** (the most frequent, not just the last), the
    **typical amount** (the median of recent entries, shown as "usually $8–$12"), and the
    **usual account**.
  - Past notes appear as a pick list, never pre-filled.
  - The more recent and frequent, the stronger the suggestion. One-off entries don't count.
- **Time patterns (the "timed basis" part):**
  - Spot entries that repeat on a schedule: the same payee and a similar amount at regular
    intervals, such as the same day each month or every other Friday.
  - Offer: "Spotify has appeared on the 15th for 4 months. Make it a bill?" One click opens the
    bill editor, pre-filled.
  - Optionally, "you usually log Quickmart on Tuesdays" can rank suggestions by weekday. It's never
    a nag.
- **Controls:** a "Don't suggest this" option per suggestion. Settings can turn off pattern
  detection. It's all computed locally from your own transactions.

**Rules:** thresholds (for example, at least three occurrences, a regular interval within ±3 days,
and amount variation under 20% to call something recurring) are written down and tested.

**Tests:** a fixed history produces a fixed set of suggestions, with edge cases like payees in
different letter cases, a changed category, and irregular spacing.

**Open question:** is the note suggestion for things like "gas" or "lunch w/ Sam" that you retype
often? That changes whether notes are learned per payee or globally.

## 1. Bank import with review (2.3.0, L)

> **Example CU formats:** Example CU's download offers **CSV** (confirmed by the user) and **QFX**
> (Quicken's OFX format). Import supports both through one pipeline:
> - **QFX/OFX** is a standard layout (no column mapping), and every transaction has a bank ID
>   (`FITID`), which makes duplicate detection exact.
> - **CSV** uses the per-account column mapping below. Example CU's layout is recognized from its header
>   row once the user shares that row plus one made-up row.
>
> Both are parsed locally by small parsers in Core. No library or Quicken is needed.

**Goal:** bring a bank or card export into Ledger in a minute, with nothing saved until you've
reviewed it and no duplicates.

**Pipeline (brief §25):** file → parser → normalized rows → categorize (uses #6) → duplicate check
→ **review** → save as one batch.

**Build:**
- **Column mapping per account, remembered.**
  - The first import asks which column is the date, amount (or separate debit and credit
    columns), description, and optional memo and reference number.
  - It also asks the date format and which sign means money out.
  - Saved as that account's import profile, so later imports are automatic. Common layouts can be
    detected from the header row.
- **Review screen:** every row with a suggested payee (cleaned from the bank's description),
  category, and type (spending, income, refund or transfer).
  - Rows are grouped as new, **likely duplicate**, or needs attention.
  - You can edit any row, skip rows, or accept all.
- **Duplicates (brief §26):**
  - An exact match on the bank's reference number means "already imported". It's stored in the
    existing `ExternalId`.
  - Otherwise, the same account and amount within ±3 days, with a similar payee, means a
    **likely duplicate**. This covers entries you typed in by hand first.
  - Likely duplicates are unticked by default, never silently dropped or silently added.
- **Transfers:** a withdrawal in one account matching a deposit in another (same amount, ±3 days)
  is offered as one transfer, never two transactions.
- **Bills:** imported rows matching a bill's due date can be linked to that occurrence, so it
  counts as recorded.
- **Undo:** every import is one batch, and "Undo this import" removes exactly that batch. This
  needs an `ImportBatchId` on transactions.
- **Privacy:** the file is read locally and never copied or uploaded. Raw bank descriptions are
  stored only in the memo if you choose.

**Formats:** QFX/OFX and CSV (Example CU offers both). QFX uses the bank's transaction IDs for exact
duplicate detection. CSV uses the column mapping above and the date, amount and payee matching.

**Tests:**
- Parsing each supported layout, sign conventions, dates, and thousand separators.
- Duplicates by reference and by fuzzy match, transfer pairing, and undo.
- Importing the same file twice adds nothing.

**Open question:** which banks and cards? For example, Example CU for savings, plus your checking
account and any card. **Please export one CSV from each and share only the header row and one
row with made-up numbers.** Each bank's format differs, and real samples beat guessing.

## 2b. Statement reconciliation (2.4.0, M)

**Goal:** confirm Ledger matches a bank or card statement, and find the difference when it
doesn't.

**Build:**
- **Reconcile an account:** enter the statement's end date and ending balance.
  - Ledger lists that account's unreconciled transactions up to the date, and you tick the ones
    on the statement.
  - A running "difference" shows how far off the ticked total is from the statement. At $0.00,
    **Finish** marks them Reconciled and saves the reconciliation (date, balance).
- **Reconciled transactions are protected:** editing one asks for confirmation, because it would
  break a past statement match.
- **Helpers:** highlight likely causes of a difference, such as a transaction dated just after
  the statement, a pending one, or an amount with transposed digits.
- **Card statements:** the "statement balance" is money owed, matching how credit cards already
  work.

**Tests:** a difference at every step, finishing only at zero, protecting reconciled
transactions, and several statements in a row.

## 3. Sinking funds (2.5.0, M)

**Goal:** set money aside for known future costs (car repairs, gifts, the annual insurance bill)
so it isn't mistaken for money you can spend.

**Design (keep it light, brief §14: no full envelope budgeting):**
- A **sinking fund** is a goal with a purpose. You have a target and date, or a monthly
  set-aside, plus an optional linked spending category (e.g. "Car repairs" → Transportation ›
  Maintenance).
- **Setting money aside:**
  - Monthly, from the budget: the fund's amount appears in the budget as a planned line.
  - Or anytime, by hand (like goal contributions).
  - Setting aside **never moves money between accounts**. It's an earmark, like goals today.
- **Spending from a fund:** when you record spending in the linked category, Ledger offers "Pay
  this from Car repairs?" That lowers the fund and keeps the budget honest.
- **Overview:** "Available" gains a companion line, "Set aside for funds −$X → **Free to spend
  $Y**". Available itself doesn't change meaning.
- **Rules:** a fund can't go below zero, and set-asides can't exceed the money available in the
  covered accounts (warned, not blocked).

**Open question:** should "Free to spend" replace "Available" as the big number on the Overview,
or sit beneath it? That's a visible choice about what Ledger treats as your money.

## 5. Scenario planning (2.6.0, L)

**Goal:** answer "what if" questions safely. **Nothing in a scenario is ever saved as real
data**, and scenarios are clearly labelled.

**Build:**
- A **Scenario** is a named set of assumptions applied to the forecast:
  - **Hours change:** "shifts × 75% from Nov 1" or "20 hours a week", which re-runs paycheck
    predictions with taxes.
  - **One-off purchase:** "$1,200 laptop on Dec 5, from Checking".
  - **Income or bill change:** add, remove or change a recurring item from a date.
  - **Pay rate change.**
- **Compare:** the baseline forecast and the scenario side by side over 30–180 days.
  - Shows the **lowest balance and its date**, ending balance, and the dates the balance goes
    below zero or below a cushion you set.
  - Shows **goal impact**, e.g. "the MacBook target slips from June to August" or "needs
    $58/month instead of $42".
- **"Can I afford this?"** is a shortcut: enter an amount and date, and get a plain answer.
  - "Yes, lowest point $312 on Dec 12" or "Not without dipping below $0 on Dec 12 (by $88)".
  - It shows every assumption used.
- **Saved scenarios** can be reopened, but never touch transactions, bills or goals. "Make this
  real" is an explicit, separate action per item (e.g. create the bill).
- **Built on:** `ForecastService` gains an overlay input (extra events, paycheck adjustments), so
  scenario math is the forecast math.

**Tests:**
- A scenario never writes: extend the "reads never write" invariant.
- Hour changes re-price paychecks with taxes and overtime.
- Purchase timing, goal-date shifts, and cushions.

## Across all of V2

- **Data safety:**
  - Each feature that changes the database ships with a migration that is tested against a real
    1.9 database, and the automatic pre-upgrade backup continues.
  - Migrations are always read and hand-checked. The Entity Framework scaffold guessed wrong
    twice in V1.
- **Docs:**
  - RULES.md gains each feature's rules, with the tests that enforce them.
  - EXPORT_FORMAT.md goes to format version 2 with refunds and import batches.
  - V1.md's "yearly upkeep" still applies. `tax-2027.json` is due by January.
- **Tests:** the invariant tests are extended for every feature that touches money (conservation,
  pages agreeing, reads never writing). `scripts/smoke-test.ps1` grows a step per feature.
- **Size:** none of this needs new large libraries. CSV parsing is small and written in Core, so
  it stays portable to Swift.
- **Out of scope:** bank connections (APIs), cloud sync, investments, and AI. Suggestions are
  statistics over your own data, not AI.

## Decisions (September 27, 2026)

1. **Paystub:** no deductions on Riverside Market pay that the user knows of. #4 still ships deduction
   support, but the paystub comparison is the main value.
2. **Banks:** Example CU first. It exports both CSV and QFX (see #1). QFX needs no sample. For CSV, the
   Example CU header row (plus one made-up row) is needed before import is built. The first real import
   goes through the review screen, so nothing is saved unseen.
3. **Sinking funds:** "Free to spend" sits as a line **under** Available. Available keeps its meaning.
4. **Autofill notes:** learned **globally** (across all entries), not per payee.
5. **Order:** the recommended order, 4 → 2a → 6 → 1 → 2b → 3 → 5.
